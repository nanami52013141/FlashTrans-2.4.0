# FlashTrans 2.4.0 改造说明（GPU 加速 + 窗口拖拽优化 + GGUF 稳定性 + 机械术语）

在官方开源版本 `flashtrans-next`（v2.4.0，Tauri + Rust + Python 桥接）基础上改动，目标：
1. **翻译走显卡**：本地 NLLB / Opus-MT 翻译（CTranslate2）自动探测并使用 NVIDIA CUDA；
2. **GGUF 大模型走显卡**（可选）：Rust llama.cpp 在编译时启用 CUDA 后，自动把模型层卸载到 GPU；
3. **窗口拖动不卡**：拖拽时临时关闭重绘开销大的 CSS 特效，松手恢复，外观不变；
4. **GGUF 纠错/对话闪退修复**：修正上下文 `n_batch` 与喂入块大小相等的越界崩溃；
5. **机械工程术语校正**：新增术语库层，统一 1.3b / 3.3b 两个 NLLB 模型在机械词上的译名；
6. **出安装包（setup.exe）**：通过 Tauri 自带 NSIS 打包，并可额外用 Inno Setup 还原原版命名。

> 原版只把推理强制跑在 CPU（`device="cpu"`），且透明 + 亚克力 + 阴影窗口在移动时整窗每帧重绘，集显/老机器上会明显卡顿。本改动解决这两点，并额外修了 GGUF 闪退、补了机械术语。

---

## 一、改动清单

| 文件 | 改动 |
|------|------|
| `backend_bridge.py` | 新增 `_cuda_available()` / `ct2_device()` 自动探测；`Ct2Translator` 构造时 `device` 由 `ct2_device()` 决定（默认自动，CUDA 初始化失败自动回退 CPU）。可用环境变量 `FLASHTRANS_DEVICE=cuda\|cpu` 强制。翻译出口接入 `apply_glossary()` 做机械术语校正。 |
| `mechanical_glossary.py`（新增） | 机械工程术语表（中英对照 + 常见错误译法）+ 方向感知的译名校正函数 `apply_glossary()`；支持 `mechanical_terms.json` / `FLASHTRANS_GLOSSARY` 自定义扩充。 |
| `src-tauri/src/gguf.rs` | 新增 `n_gpu_layers()`；模型加载 `with_n_gpu_layers(0)`（=全放 CPU）改为 `with_n_gpu_layers(n_gpu_layers())`（默认 `i32::MAX`=全部卸载到 GPU；无 CUDA 构建时自动忽略）。**关键修复**：`generate()` 的上下文显式 `.with_n_batch(1024)`，避免长输入恰好填满默认 512 容量触发 llama.cpp 原生崩溃（闪退根因）。可用环境变量 `FLASHTRANS_GPU_LAYERS` 覆盖（0=纯 CPU）。 |
| `src-tauri/Cargo.toml` | 新增 `[features] cuda = ["llama-cpp-2/cuda"]`。默认不启用（GGUF 走 CPU，构建无需 CUDA）；启用后 GGUF 走显卡。 |
| `src/drag.ts`（新增） | 拖拽优化核心：监听标题栏拖拽，给 `<body>` 挂/摘 `.dragging` 类。 |
| `src/main.ts` `popup.ts` `chat.ts` `pin.ts` `overlay.ts` | 各页面 `import` 并调用 `installDragPerf()`。 |
| `src/theme.css` | 新增 `body.dragging` 规则：拖拽期间关掉 `box-shadow / transition / animation / backdrop-filter / filter`。 |
| `src-tauri/tauri.conf.json` | `bundle.resources` 加入 `bridge` 目录，保证安装包把翻译桥接 `flashtrans-bridge.exe` 打进安装根目录（与 `FlashTrans.exe` 同级）。 |
| `installer/FlashTrans.iss`（新增） | Inno Setup 脚本，还原原版 `FlashTrans-2.4.0-Setup.exe` 安装样式（安装到 `AppData\Local\Programs\FlashTrans`、桌面快捷方式、`bridge/` 随包分发）。 |
| `build.ps1` | 新增 `-Inno` 开关：在 Tauri NSIS 包之外，额外用 ISCC 打出原版命名的安装包。 |

> 说明：OCR（RapidOCR）仍走 CPU —— 截图识别本身很快，不是瓶颈，且改 GPU 需换 `onnxruntime-gpu` 并可能破坏冻结后的桥接，故保持原样。

## 二、构建环境（在你自己的 Windows 机器上）

- **Node.js 18+**（含 npm）—— 编译前端。
- **Rust 工具链**（rustup + stable） + **Visual Studio Build Tools / MSVC** + **Windows SDK** —— 编译 Tauri/Rust 主程序。
- **WebView2 运行时**（Windows 10/11 一般自带；没有则从微软下载常青版）。
- **Inno Setup 6**（若用作者自带的 Inno 脚本出安装包；Tauri 自带的 NSIS/WiX 也可，见下文）。
- **仅当要 GGUF 也走显卡时**：安装 **CUDA Toolkit 12.x**（与 `llama-cpp-2` 编译时的 CUDA 版本匹配），并在构建时加 `--features cuda`。
- **Python 3.11+**（仅用于冻结翻译桥接 `flashtrans-bridge.exe`）：`python -m venv .venv` 后 `.\.venv\Scripts\pip install -r requirements-bridge.txt pyinstaller`。

> 本机（生成环境）没有 Rust / Inno Setup，无法在此直接产出 `.exe` 安装包；以上步骤在你的 Windows 机器上执行即可。

## 三、构建步骤

### 1) 前端
```powershell
cd flashtrans-next
npm install
npm run build          # = tsc + vite build，输出到 ../dist
```

### 2) 冻结翻译桥接（Python → flashtrans-bridge.exe）
```powershell
# 仓库根目录创建并装好 .venv（见“构建环境”最后一条）
.\scripts\build_bridge.ps1
# 产物：installer\bridge-dist\flashtrans-bridge\flashtrans-bridge.exe
```
> `ctranslate2` 的 PyPI wheel 自带 CUDA 运行时，冻结后会一起打进 exe；目标机有 NVIDIA 显卡即可走 GPU。

### 3) 出安装包
- **GGUF 只走 CPU（默认，推荐先这么出）**：
  ```powershell
  cargo tauri build
  ```
- **GGUF 也要走显卡**（需已装 CUDA Toolkit）：
  ```powershell
  cargo tauri build --features cuda
  ```
- 产物在 `src-tauri\target\release\bundle\`（含 NSIS 安装包 `FlashTrans_2.4.0_x64-setup.exe`，依 Tauri 配置而定）。
- **还原原版命名 `FlashTrans-2.4.0-Setup.exe`**：装好 Inno Setup 6（ISCC.exe 在 PATH）后，加 `-Inno`：
  ```powershell
  .\build.ps1 -Inno        # 或 .\build.ps1 -Gpu -Inno
  ```
  脚本会用 `installer\FlashTrans.iss` 打出与原版同名的安装包（安装样式一致：仅当前用户、桌面快捷方式、`bridge/` 随包）。
- **模型文件不随包分发**：安装完成后，把下载的 `models` 文件夹整体复制到安装目录下（与 `FlashTrans.exe`、`bridge` 同级），再在软件设置里添加模型即可（同原版教程）。

## 四、运行前提 & 环境变量

- **翻译 GPU 生效条件**：目标机器有 **NVIDIA 显卡 + 较新驱动**。程序启动翻译时自动探测（`nvidia-smi`）；也可在启动前强制：
  ```powershell
  $env:FLASHTRANS_DEVICE = "cuda"   # 或 "cpu" 强制回退
  ```
- **GGUF GPU 生效条件**：必须用 `--features cuda` 构建过，且目标机有 NVIDIA 显卡。可用环境变量微调卸载层数：
  ```powershell
  $env:FLASHTRANS_GPU_LAYERS = "99"   # 卸载 99 层；0 = 纯 CPU；省略=全部卸载
  ```
- 没有 NVIDIA 显卡时，上述全部自动回退 CPU，程序照常可用，只是不走加速。

---

## 五、验证 GPU 是否生效

- **翻译（CTranslate2）**：打开任务管理器 → 性能 → GPU，划词翻译时看 GPU 占用/显存是否上升；或在启动前设 `FLASHTRANS_DEVICE=cuda`，若机器无 GPU 会在加载模型时回退并打日志（可在开发者控制台/日志看到）。
- **GGUF**：用 F4 对话或大模型翻译时观察 GPU 占用；`FLASHTRANS_GPU_LAYERS=0` 可强制其走 CPU 做对比。

## 六、常见问题

- **OCR 仍然偏 CPU**：符合预期，OCR 不是瓶颈，保持原样以保证桥接冻结稳定。
- **拖拽还是有点卡**：本改动已关掉 CSS 重绘开销最大的几项。若仍卡，多半来自窗口的 OS 级“亚克力”+“阴影”合成——可在 `src-tauri/tauri.conf.json` 里把对应窗口的 `"shadow": true` 改为 `false`，或在 `src/drag.ts` 里进一步在拖拽时临时调用 Tauri 的 `setEffects([])` 关闭亚克力（已留好钩子位置，按需启用）。
- **CTranslate2 报缺 `cudart64_*.dll` 等 CUDA 运行时**：更新 NVIDIA 驱动，或安装与 ctranslate2 wheel 匹配的 CUDA 12 Runtime。
- **`cargo tauri build --features cuda` 失败**：确认已安装 CUDA Toolkit 且版本与 `llama-cpp-2` 期望一致；不想折腾就直接默认（CPU）构建，翻译 GPU 仍可用。

## 七、机械工程术语库（自定义扩充）

NLLB-200 是固定训练好的模型，**无法向 `.bin` 里直接“加词”**（那等于重训练，本环境也做不了）。
两尺寸（1.3B / 3.3b）对同一机械词常给出不同、甚至明显偏差的译名，这是容量差异的
固有现象。本改动在翻译*结果*上加一层确定性术语校正来弥补：

- 当**原文**出现了某个机械术语、而**译文**却没出现规范译名、反而出现了已知错误译法时，
  把错误译法替换成规范译名。只在“明显译错”时动手，**绝不凭空注入**，因此对 1.3b 和 3.3b
  都安全，且能把两者的领域译名统一到同一套规范词表，缩小“差距很大”的问题。
- 内置术语见 `mechanical_glossary.py` 的 `MECH_TERMS`（轴承/齿轮/紧固件/材料/加工/液压/电机等）。
- **自行扩充**：在 `mechanical_glossary.py` 同级放一个 `mechanical_terms.json`，格式：
  ```json
  [
    {"en": "bearing", "zh": "轴承",
     "wrong_en": ["support", "holder"], "wrong_zh": ["支承", "轴承座"]}
  ]
  ```
  程序启动翻译时自动合并；也可用环境变量 `FLASHTRANS_GLOSSARY` 指向任意 JSON 文件。
  其中 `wrong_en` 是 ZH→EN 时会被纠正的错误英文，`wrong_zh` 是 EN→ZH 时会被纠正的错误中文。
- 想完全关闭该层：把 `backend_bridge.py` 里 `apply_glossary(...)` 那行注释掉即可。
